### 2026-09-11 - Production Mobile Authentication Fix (80% / 100%, Milestone 09 NOT STARTED)
- Scope: urgent production bug - the real Admin account (Eng. Mohamed Elhabak) could log in from desktop browsers but not reliably from a real mobile phone, with the client specifically describing credentials sometimes copied out of a WhatsApp Arabic/RTL conversation. No credentials, hashes, or secrets appear anywhere below or in any commit/test file.
- **Reproduction discipline followed exactly as required - no fix attempted before the failure was isolated with live evidence against the production API:**
  - Baseline: a clean `POST /auth/login` against `https://elhabak-api-production.up.railway.app` with the real Admin email/password returned `200`, and the returned session cookie correctly round-tripped to `GET /auth/me` (`200`, correct user) - confirmed via direct HTTP calls, not browser guesswork.
  - The `Set-Cookie` header was inspected directly: `HttpOnly; Secure; SameSite=None; Path=/`, and `Access-Control-Allow-Origin` was the exact web origin (not a wildcard) with `Access-Control-Allow-Credentials: true`. This is the standards-correct configuration for the deployment's separate-domain web/API architecture, and the login-to-`/auth/me` round trip worked correctly over raw HTTP - so hypothesis B ("login succeeds but the session cookie isn't retained") was tested and found **not** to be the root cause. No same-origin reverse-proxy re-architecture was implemented, since none was evidenced as necessary and it would have been a large, high-risk change to make on an unconfirmed hypothesis.
  - Hypothesis A was then tested directly: the same login request was repeated with the email deliberately contaminated with zero-width/bidirectional-control Unicode characters (LRM, RLM, a BOM) of the kind mobile clipboards commonly embed when text is copied out of an RTL (Arabic) message - exactly the scenario described. Plain leading/trailing whitespace and a trailing clipboard newline already worked (pre-existing `.trim()` handled those), but the bidi-control-mark variants reproducibly returned **`400 Bad Request`**, not `401` - the request never reached password comparison or cookie logic at all. It failed at Zod schema validation (`emailSchema = z.string().trim().email()`), because `.trim()` only removes whitespace, and these Unicode control marks are not whitespace, so `.email()` rejected the value as a malformed address.
  - **Exact root cause:** `packages/validation/src/index.ts`'s shared `emailSchema` did not strip invisible Unicode bidi-control/zero-width characters before validating the address format, so a real phone pasting an email out of an RTL WhatsApp conversation could get a `400` on every login attempt with the technically-correct credentials.
- **Fix implemented (`packages/validation/src/index.ts`):**
  - `emailSchema` now strips zero-width/bidi-control characters (ZWSP/ZWNJ/ZWJ/LRM/RLM, LRE/RLE/PDF/LRO/RLO, LRI/RLI/FSI/PDI, and BOM) and trims whitespace *before* the `.email()` format check, via `z.string().transform(stripInvisibleUnicode).pipe(z.string().email().max(254))`. This is the single shared schema used by login, user creation, and client creation, so every email entry point in the system is hardened consistently, not just login.
  - `loginSchema`'s password field now strips only a trailing carriage-return/line-feed (a real clipboard-paste artifact from some mobile messaging apps), via a small `stripTrailingClipboardNewline` helper. The password is never lowercased, trimmed of interior/leading/trailing spaces, or Unicode-normalized - any other character, including a deliberate leading/trailing space, is preserved exactly, and bcrypt comparison semantics are unchanged.
  - No character-stripping logic was implemented using literal Unicode escape sequences in source text (an early attempt in this session to embed literal invisible Unicode characters directly in source text silently produced actual invisible characters in the file instead of escape-sequence text - caught immediately by inspecting the file byte-by-byte with a Node script before it was ever committed). Every stripping function in both the shared schema and the login form instead builds its character ranges from plain numeric code points (`0x200b`, `0xfeff`, etc.), which is safer, more portable, and easier to review than embedding invisible characters in source.
  - `apps/web/src/app/login/login-form.tsx`: mirrors the same stripping client-side (`normalizeEmailForSubmit`) so the user sees the clean value before it's even sent - the server remains the authoritative check regardless. Hardened both inputs for mobile: `inputMode="email"`, `autoComplete="username"`/`"current-password"`, `autoCapitalize="none"`, `autoCorrect="off"`, `spellCheck={false}` on both fields, so the mobile keyboard/browser cannot silently auto-capitalize or autocorrect the credentials before submit.
