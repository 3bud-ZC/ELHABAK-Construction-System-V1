Test-only mitigation added: `apps/api/src/test-database-env.ts` (a Vitest `setupFiles` entry) rewrites `DATABASE_URL` to the direct URL with conservative `connect_timeout`/`pool_timeout`/`connection_limit` parameters for the test process only; the running application in dev/production is unaffected and continues to use the pooled `DATABASE_URL` as configured. This does not weaken or hardcode any credential - both URLs come from the existing ignored `.env`.
- Same pre-existing Neon pooled-connection sequential-bootstrap flakiness recurred once during Milestone 08's full-suite run: `milestone-05.spec.ts` (Site Operations, unrelated to Milestone 08) timed out on one test with an `ENOENT` file-write error while six other spec files in the same run passed cleanly; re-running `milestone-05.spec.ts` alone immediately afterward passed 6/6 in 32 seconds, confirming environment flakiness under sequential load rather than an application or Milestone 08 regression.
- Fixed a real pre-existing architectural bug found during Milestone 08's own bootstrap: `apps/api/src/main.ts` statically imported `AppModule` at the top of the file, which (being a synchronous `require()` in the compiled CommonJS output) evaluated the entire provider graph - including any module-load-time `process.env` read - before `bootstrap()`'s own `config({quiet:true})` dotenv call ever ran. This had not surfaced before because no existing provider read `process.env` at module-load time (the established convention, e.g. `AuthService`/`StorageService`, reads env inside a class field, which only evaluates once Nest constructs an instance after bootstrap). Milestone 08's `RealtimeGateway` needed its CORS origin at `@WebSocketGateway()` class-decorator evaluation time (which also runs at module load, not construction), which no lazy-field pattern can defer - so the real fix was changing `main.ts` to dynamically `await import("./modules/app.module")` after `config()` runs, matching the pattern every `*.spec.ts` file already used for exactly this reason. Production/dev bootstrap only; no behavior change for any existing module.

This is the standards-correct configuration for the deployment's separate-domain web/API architecture, and the login-to-`/auth/me` round trip worked correctly over raw HTTP - so hypothesis B ("login succeeds but the session cookie isn't retained") was tested and found **not** to be the root cause. No same-origin reverse-proxy re-architecture was implemented, since none was evidenced as necessary and it would have been a large, high-risk change to make on an unconfirmed hypothesis.
  - Hypothesis A was then tested directly: the same login request was repeated with the email deliberately contaminated with zero-width/bidirectional-control Unicode characters (LRM, RLM, a BOM) of the kind mobile clipboards commonly embed when text is copied out of an RTL (Arabic) message - exactly the scenario described. Plain leading/trailing whitespace and a trailing clipboard newline already worked (pre-existing `.trim()` handled those), but the bidi-control-mark variants reproducibly returned **`400 Bad Request`**, not `401` - the request never reached password comparison or cookie logic at all. It failed at Zod schema validation (`emailSchema = z.string().trim().email()`), because `.trim()` only removes whitespace, and these Unicode control marks are not whitespace, so `.email()` rejected the value as a malformed address.
  - **Exact root cause:** `packages/validation/src/index.ts`'s shared `emailSchema` did not strip invisible Unicode bidi-control/zero-width characters before validating the address format, so a real phone pasting an email out of an RTL WhatsApp conversation could get a `400` on every login attempt with the technically-correct credentials.
- **Fix implemented (`packages/validation/src/index.ts`):**
  - `emailSchema` now strips zero-width/bidi-control characters (ZWSP/ZWNJ/ZWJ/LRM/RLM, LRE/RLE/PDF/LRO/RLO, LRI/RLI/FSI/PDI, and BOM) and trims whitespace *before* the `.email()` format check, via `z.string().transform(stripInvisibleUnicode).pipe(z.string().email().max(254))`. This is the single shared schema used by login, user creation, and client creation, so every email entry point in the system is hardened consistently, not just login.
  - `loginSchema`'s password field now strips only a trailing carriage-return/line-feed (a real clipboard-paste artifact from some mobile messaging apps), via a small `stripTrailingClipboardNewline` helper. The password is never lowercased, trimmed of interior/leading/trailing spaces, or Unicode-normalized - any other character, including a deliberate leading/trailing space, is preserved exactly, and bcrypt comparison semantics are unchanged.
